# Guarded voice commissioning

## Optional NOLAN conversation

Merging the conversational voice code enables nothing. The existing command
catalogue and safety decisions stay authoritative. To opt in, set
`JARVIS_VOICE_CONVERSATION_PROVIDER=anthropic` and supply `ANTHROPIC_API_KEY`
or `ANTHROPIC_AUTH_TOKEN` to the server process environment. The default model is `claude-opus-5-5`;
`JARVIS_VOICE_CONVERSATION_MODEL` selects another model. Remove or unset the
provider selector to disable paid conversation even if a key remains present.
The status API reports the provider, model and configuration reason without a
key or a live provider probe. Unknown provider values disable conversation.

**Free-form changes (Client profile).** With conversation on, NOLAN also
understands changes said in your own words: `Nolan, chuck some bar oil on the
shopping list`, `Nolan, I've sorted the milk`, `Nolan, push the rego reminder
to Friday at 9`. The model may propose exactly one change through its
`propose_change` tool: add a task, reminder or errand; tick off a task or
errand; cancel a reminder; remove an errand; or reschedule a reminder. It
cannot stage anything itself. NOLAN turns the proposal into its own canonical
sentence (`add an errand: Bar oil`) and runs it through the ordinary dictation
path, so every rule above applies unchanged: record lookup, refusing ties and
vague words, the bounded due-time grammar, the full read-back, `Nolan confirm`,
and owner approval on the Approvals page. A proposal that the grammar refuses,
or one made alongside a query, is reported as not understood and arms nothing.
A due time outside the bounded grammar (`next Friday`, `in two hours`) is
refused rather than folded into the title. Speech the deterministic grammar
already understands never reaches the model.

Only a final, wake-authorised utterance that the deterministic session returns
as unrecognised reaches the conversation provider. **Enabling this sends the
wake-authorised utterance text and the read-only answers the model asks for to
the provider.** It also sends the short in-memory conversation history and the
active profile's catalogue phrases and summaries. It does not send raw business
records, extra project or client identifiers, approval tokens, ToolAction
payloads, or a provider key as model content. The SDK uses its process key for
API authentication; the key is never returned to the HUD, logged, or stored by
the conversation feature. No conversation history is saved to JSON or Convex.

The model can request only the existing read-only voice queries for the active
profile. It cannot write, stage, approve, confirm, cancel, actuate, or switch
profiles. If asked to do work, it must say it has not done it and give the
catalogue phrase instead. Model-initiated actions require a later, separate
reviewed change.

Defaults: 120 model calls per rolling hour per server process, 500 characters
per utterance, 600 characters per spoken reply, 12 recent user/assistant
messages per voice session, four model turns per utterance, and a 20-second
request timeout. The first five limits can be adjusted with
`JARVIS_VOICE_CONVERSATION_MAX_CALLS_PER_HOUR`,
`JARVIS_VOICE_CONVERSATION_MAX_UTTERANCE_CHARS`,
`JARVIS_VOICE_CONVERSATION_MAX_REPLY_CHARS`,
`JARVIS_VOICE_CONVERSATION_HISTORY_MESSAGES`, and
`JARVIS_VOICE_CONVERSATION_TIMEOUT_MS`. Invalid limits disable conversation.
History is discarded when the voice session ends, expires (an expiry sweep runs
at least once a minute), is evicted, or switches profile. Spoken text is never
model-authored: with no read-only query the fixed "I haven't done anything. Ask
a catalogue question or say a catalogue command." is spoken; with exactly one
successful query its exact answer is spoken. Several queries, an unavailable
source, or an answer longer than the reply limit give a plain
conversation-unavailable notice (`tool-limit`, `unavailable`, `reply-too-long`);
the answer is never truncated. A later utterance, or a confirmation
armed meanwhile, cancels a reply still in progress. A limit or provider failure appears as a plain notice; the
browser does not speak a fabricated answer.

This runbook commissions the browser/HUD voice path from speech or typed input to the Jarvis voice HTTP boundary. It does **not** prove physical equipment control. Main uses `AbsentHardwareProvider`, so every actuation target must remain unavailable until a separately reviewed hardware adapter is installed and commissioned.

## Preconditions

1. Work from the exact PR candidate SHA being evaluated.
2. Run `npm run check` and `npm run openapi:lint` from `typescript/`; both must pass.
3. Start the local preview with `npm run start:preview` and open the HUD on the loopback address it reports.
4. Do not expose the preview to a non-loopback interface merely to test voice. Off-loopback voice routes retain normal service-token/OIDC authentication.

## Approving staged changes

Open `/settings/approvals` (linked from the HUD Approvals panel) on the loopback HUD host. Type the service token and the approval token; they stay in the page only until you leave it and are never written to browser storage. **Load staged actions** lists everything waiting on the `nolan-voice` project (or another project key), each with NOLAN's read-back (`Mark task “Order bar oil” done`) and the exact operation and arguments. **Approve and run** approves that one action with your approval token and then runs it once; **Reject** discards it. Approved actions can be run again safely: a repeat returns the original result and changes nothing. The page uses only the existing tool-action routes and adds no authority; off loopback it is not served.

## Browser and typed checks

1. Open **Voice**. Record browser/OS and whether the HUD reports **MIC AVAILABLE** or **TYPED ONLY**.
2. With no microphone enabled and the **Client** profile selected, type a read-only command such as `Jarvis any unpaid invoices`. A healthy empty invoice register is reported as none, not as a guessed count. If the invoice register cannot be read, the HUD names invoice records as unavailable. Recognizing the command must never be presented as an answered business query when its source is unavailable. Live workshop, crawler and trailer hardware status stays unavailable until a hardware adapter is commissioned. Recorded crawler or trailer status, when the build register can be read, names only builds whose kind records that equipment.
3. Type an unknown phrase. Confirm it is rejected/unrecognised and nothing becomes pending.
4. A typed safe write (`Jarvis add a task`, `Jarvis remind me to follow up`) stages a ToolAction only when the utterance starts with `Jarvis`, a commissioned project target is supplied, and the capture includes the required title (and, for a task, a category). Punctuation or whitespace right after `Jarvis` (`Jarvis, add a task`, `Jarvis. add a task`, `Jarvis? add a task`) is the same wake word. A longer word such as `Jarvisx` is not. A missing or blank reminder title is incomplete and must write nothing. Without the wake word the phrase may be recognised and must write nothing. Spoken confirmation never approves a quote send, a draft, or any other consequential proposal. The microphone path keeps the stripped command and sends the original wake-word transcript as `heardTranscript`. Voice never approves or executes. The staged action id includes the expected project revision, so a retry of the same revision is the same proposal and a different revision is a different proposal.
   For inferred speech, only that accepted leading wake prefix is stripped before interpretation. `Jarvis I'd send the quote` and `Jarvis I'll send the quote` are reports: neither may leave a pending confirmation, and a later `confirm` must do nothing. `Jarvis, can you send the quote?` remains an explicit request that waits for spoken confirmation and then yields only a governed proposal.
   **Spoken capture (dictation).** On the **Client** profile a wake-authorised final utterance can carry the safe write's own text: `Nolan, add a task: order bar oil`, `Nolan add a work task, quote the Smith fence`, `Nolan remind me to call Dave about the fence`. Spoken categories are `personal`, `work` (also `job`), `builds` (also `build`), `money` (also `finance`) and `life` (also `home`); an unknown word before "task" is rejected rather than guessed, and no category means `personal`, the same default as the HUD capture form. The HUD reads the capture back (`Add task “Order bar oil” (work)? Say “Nolan confirm”…`) and stages nothing until `Nolan confirm`; `Nolan cancel`, expiry, a fresh command or a profile change discard it. Confirming only stages the ToolAction with exactly the read-back fields (a request-body `capture` cannot replace them); owner approval and execution are unchanged. The dictation must start at the beginning of the utterance, may not contain a wake word or a confirm/cancel phrase, is limited to 200 characters, and never reaches queries, actuation or quotes. A recogniser alternative that is a control phrase or dictates the other command makes the turn ambiguous. Titles keep the casing the recogniser produced (`Call Dave about the BMW`, `iPhone screen repair`). Only a lower-case first word is capitalised. Matching and every safety rule stay case-insensitive, and recogniser alternatives that differ only in casing are not a conflict. If casing cannot be aligned with the matched text (a few Unicode letters change length when lower-cased), the lower-cased title is used. A dictated reminder can carry a spoken due time: `Nolan, remind me to call Dave tomorrow at 7 am`, `… on Friday at 9 am`, `… tonight at 8`, `… at 3:30 pm` (the next occurrence), or a leading phrase such as `Nolan, remind me tomorrow at 7 am to call Dave`. It is resolved in `JARVIS_TIMEZONE` with the existing reminder parser and read back as the exact time (`Add reminder “Call Dave” due Mon, 16 Nov, 7:00 am`). The confirmed ToolAction carries `dueRaw`, `dueAt` and `dueTimezone`, exactly as read back. Nothing is guessed: a day with no time (`by Friday`) or an hour with no am/pm (`at 7`, and `tonight at 12`, which could be noon or midnight) keeps the spoken text with no timestamp, and the read-back says no time is set. `next Friday` is never resolved and stays in the title. A time that has already passed (`today at 9 am` after 9), a contradiction (`tonight at 8 am`, `tonight at noon`) or an impossible time is rejected. Recogniser alternatives that disagree on the time make the turn ambiguous. Tasks never take a due time. **Errands** are dictated the same way: `Nolan, add an errand: silicone for the Smith deck`, `Nolan new errand, 2 tubes of silicone`, `Nolan add milk to the errands`, `Nolan put screws on my shopping list`. The read-back is `Add errand “Silicone for the Smith deck”?`, and `Nolan confirm` stages an `errands:create` ToolAction carrying only the title. A spoken errand never takes a category, a due time, a location or a business-project link; set those later from the HUD or `PATCH /api/v1/errands/{id}`. The bare catalog phrase `add an errand` (no title) still stages nothing. **Completing by voice.** `Nolan, tick off bar oil`, `Nolan cross off the milk`, `Nolan mark the task order bar oil done` or `Nolan complete the errand pick up the trailer` look the spoken words up among open tasks and errands. An exact title wins; otherwise the words must appear, whole and in order, in exactly one open title. NOLAN reads back that item's full title (`Mark task “Order bar oil” done?`), and `Nolan confirm` stages `tasks:complete` or `errands:complete` for that one record on the voice project. Nothing changes until you approve and execute it. Nothing is guessed: no match, or two or more equally good matches (`Nolan tick off oil`), arms nothing and says why (`2 open items match “Oil”. Say more of the title.`). Vague words (`it`, `that`, `everything`) are refused. A task can only be completed by voice if it was captured by voice (it lives in the voice project), so a task added on the HUD is named and refused, and you complete it on the HUD. Any errand can be marked done. A completion always stages on the dedicated voice project; a request that supplies its own `projectId` is refused. **Cancelling a reminder by voice.** `Nolan, cancel the bar oil reminder`, `Nolan cancel my reminder to call Dave`, `Nolan delete the reminder: renew the rego` (also `remove`, `scrap`, `drop`, `clear`) look the spoken words up among your reminders only, with the same matching rules. NOLAN reads back the full title (`Cancel reminder “Order bar oil”?`), and `Nolan confirm` stages `reminders:cancel` for that one reminder on the voice project. Nothing is cancelled until you approve and execute it. As with tasks, only reminders captured by voice can be cancelled by voice; one added on the HUD is named and refused (`Reminder “Renew the rego” was not captured by voice, so voice cannot cancel it. Cancel it on the HUD.`). No match, a tie (`2 reminders match “Oil”.`) or vague words (`cancel the reminder`, `cancel that reminder`) arm nothing, and the HUD says `Nothing cancelled.` with the reason. The bare control word `Nolan cancel` is unchanged: it only discards a pending read-back and never cancels a reminder. **Removing an errand by voice.** `Nolan, take milk off the errands`, `Nolan remove the screws from my shopping list`, `Nolan delete the errand: pick up the trailer` (also `drop`, `scrap`, `strike … off`) look the spoken words up among open errands only, with the same matching rules. NOLAN reads back `Remove errand “Milk” from the list?`, and `Nolan confirm` stages `errands:remove` for that one errand on the voice project. Nothing is removed until you approve and execute it. Removing deletes the row from `jarvis-errands.json`; to keep a record of it, tick it off instead. A done errand, no match, a tie or vague words arm nothing, and the HUD says `Nothing removed.` with the reason. If the errand is already gone when the approved action runs, the execution succeeds with `removed: false` and nothing else changes. **Daily rundown.** `Nolan, give me the rundown` (also `brief me`, `morning brief`, `daily rundown`, `what's my day look like`, `how's my day looking`, `what have I got on today`, `run me through my day`) reads one answer from the same records as the individual queries: jobs booked for today, reminders due or coming up in the next 24 hours, open tasks and open errands (`Here's your day. 1 job booked for today. Smith fence. 1 reminder due: Call Dave. …`). It is read-only: it never stages anything, and it replaces any pending read-back like any other command. The phrases must be said whole; `give me the rundown and send the quote` is not understood. A source that cannot be read is named in its place (`Reminder records are unavailable.`) rather than guessed, and if none can be read the rundown is unavailable. `what is on today` is unchanged and still reads only today's jobs. Like dictation, the rundown needs the wake word. **Rescheduling a reminder by voice (AM-017, planned; off by default).** `Nolan, move the bar oil reminder to Friday at 9 am`, `Nolan push my reminder to call Dave to tomorrow`, `Nolan reschedule the rego reminder for 3 pm` (also `shift`, `change`, `bump`) look the words up among your voice-captured reminders with the same matching rules, and resolve the new time with the same due-time rules as a dictated reminder. `next Friday`, a time that has passed, or a contradiction is refused, and a day or an hour without am/pm keeps the spoken text with no time set. NOLAN reads back the new time (`Reschedule reminder “Order bar oil” due Fri, 20 Nov, 9:00 am?`), and `Nolan confirm` stages `reminders:reschedule` for that one reminder on the voice project. Nothing changes until you approve and execute it. AM-017 is a planned action family: until you deploy the Convex functions (`reminders:rescheduleControlled`) and set `JARVIS_REMINDER_RESCHEDULE_ENABLED=true` for the server, the executor is not registered and a spoken reschedule is refused before any record is read (`Nothing rescheduled. Rescheduling reminders by voice is not enabled yet (AM-017 is planned).`). See `docs/evidence/reminder-reschedule-am-017.md` for the activation path. An errand is written only when the approved action is executed: it is added open to the same local errand file the HUD errand list reads (`jarvis-errands.json`), under an id derived from the action, so a retried execution never adds a second row. The HUD microphone sends no project or revision: the server stages against the owner's dedicated voice project (`JARVIS_VOICE_PROJECT_KEY`, default `nolan-voice`) and reads that project's current revision at confirm time, so a client never supplies or forges either. An explicit `projectId` + `expectedRevision` on the request still takes precedence. If the voice project does not exist, the confirmed result names it and tells you to run `npm run commission:voice-project`; if it cannot be read, the result says so. Either way nothing is staged.

   **Commission the voice project once.** With `PERSISTENCE_PROVIDER=convex`, `CONVEX_URL` and `JARVIS_SERVICE_TOKEN` set (or in `.env.local`), run `npm run commission:voice-project` from `typescript/`. It creates the project at revision 1 only if it is absent, never changes an existing project, and stages, approves or executes nothing. Then restart the HTTP server. Approve a staged voice write through the governed approval route, `POST /api/v1/projects/{projectId}/tool-actions/{actionId}/approve` with your `approvalToken` (see [ToolAction approval](tool-action-approval.md)), then execute it with `POST …/{actionId}/execute`. `npm run owner:approve` only approves `home:announce` actions and refuses tasks, reminders and errands. Approved tasks are created in the voice project and appear on the HUD task list; approved errands appear on the HUD errand list.

5. Select **Crawler** and submit `Jarvis crawler halt`. Confirm the HUD enters **awaiting confirmation**. Submit `Jarvis cancel`; confirm the pending command clears without actuation.
   For a two-turn ambiguity, submit `Jarvis crawler forward and turn crawler lights on`, then `Jarvis the second one`. The second turn must enter **awaiting confirmation** for crawler lights and must not actuate yet. A later `Jarvis confirm` still uses the normal single-use confirmation path. The offered choices expire after the confirmation TTL and are discarded after one final follow-up, cancel, profile change, reset or manual override; a later ordinal alone must do nothing.
   While the choice is offered the HUD shows, and speaks through browser speech where available, a prompt that lists only the command ids the server returned, in the server's order, using catalog summaries for the active profile and the plain id otherwise (at most four are listed, then a count). The prompt is display only: it holds no choice and sends nothing, and the reply is an ordinary typed or final spoken utterance on the same session. The server response does not say whether a reply is still open, so the prompt always also allows repeating the full command. Stop, a profile change, a failed or expired session, or any other result replaces the prompt. Stop, a profile change and a failed or expired session also cancel the prompt's browser speech, so it cannot keep inviting a reply to a session that is gone. Confirm/cancel conflicts and ids outside the active profile's catalog are listed as conflicting with no invitation to choose, and a malformed candidate list shows the generic ambiguous message.
   A follow-up that names an opposite command, reports an action already taken, asks whether it happened, or conflicts with a recogniser alternative must leave no pending confirmation. After an offer expires, a fresh wake-authorised request follows the normal interpreter path on that same turn.
6. Repeat `Jarvis crawler halt`, then submit `Jarvis confirm`. On the uncommissioned main hardware provider the result must be **actuation unavailable / failed closed**. Any successful actuation acknowledgement at this stage is a stop condition.
7. Change profile while a critical command is pending. Confirm the pending confirmation is invalidated and the microphone is aborted. Enable the microphone again explicitly to resume recognition in the acknowledged profile.
8. Select **Workshop**, submit `Jarvis start the compressor`, then `Jarvis stop the compressor`. Confirm the earlier start is no longer pending and a later `Jarvis confirm` does nothing.
9. Interrupt a dispatch or recognition with **Stop**. Confirm buffered recognition and late responses cannot dispatch, restore pending state or restart speech. Already-submitted server operations cannot be undone by stopping the browser.
10. Change profile while session creation or a dispatch is in flight. Confirm old responses do not restore the previous profile or pending state. A failed profile switch must block dispatch until a profile is selected again and acknowledged.
11. After an expired-session response, submit a fresh command. Confirm a new session is created without replaying the failed utterance or carrying over its pending confirmation.

## Microphone checks

Only run these when the browser reports speech recognition support and the operator explicitly presses **Enable microphone**.

1. Speak `Nolan any unpaid invoices` (and the legacy `Jarvis any unpaid invoices`). Both must dispatch from the microphone; `Nolanx …` must not. Before the 2026-11-15 fix the HUD microphone path only woke on `Jarvis`, so spoken `Nolan` commands were silently dropped in the browser even though the server accepted them.
2. Speak a command without the wake word. It must not dispatch. A safe write spoken without the wake word must not stage a task or reminder.
3. Speak `Jarvis crawler status` after selecting **Crawler**. Only a final recognition result may dispatch.
4. Arm a critical command with `Jarvis crawler halt`, then use `Jarvis cancel`; confirm it disarms.
5. Arm it again and use `Jarvis confirm`; with no hardware adapter the result must still fail closed. `Jarvis confirmed` is accepted as the same confirmation, because browsers often transcribe a spoken "confirm" that way. Sound-alikes such as `Jarvis concern` must be rejected and leave the confirmation pending.
6. Press **Stop** while recognition or TTS is active. Confirm recognition is aborted and speech output is cancelled, including final results or responses arriving after the button press.
7. Leave the microphone enabled and stay silent for a minute. The browser ends a listening session after a silence or a network interruption; the HUD starts a new one, so **Enable microphone** stays disabled and the next `Jarvis` command is still heard. Listening ends only on **Stop**, a profile switch, a browser error that must not be retried (`not-allowed`, `service-not-allowed`, `audio-capture`, `language-not-supported`, or `aborted`, which includes cancelling speech input in the browser's own UI), or three sessions in a row that each end within two seconds. The last two show a notice and re-enable the button; the notice includes the browser's error code when the browser supplies one.
8. After `npm run commission:voice-project`, with no project target on the request, speak `Nolan add a task: test dictation`. Confirm the HUD reads it back and nothing is staged, then speak `Nolan confirm` and confirm exactly one ToolAction is staged with that title and category `personal` and is awaiting owner approval on the `nolan-voice` project. Speak `Nolan confirm` again; nothing further may be staged.
9. Speak `Nolan add an errand: test errand`. Confirm the read-back says `Add errand “Test errand”` and nothing is staged. Speak `Nolan confirm` and confirm exactly one `errands:create` ToolAction is staged with only that title, and the HUD errand list is unchanged. Approve and execute it on the governed route, then confirm one open errand `Test errand` appears on the HUD errand list. Execute the same approved action again and confirm no second errand appears.
10. Speak `Nolan tick off test errand`. Confirm the read-back names `Test errand` and nothing changes. Speak `Nolan confirm`, approve and execute the staged `errands:complete` action, and confirm the errand shows as done. Speak `Nolan tick off test` while two open items contain `test`, and confirm nothing is armed and the HUD says how many match.
11. Speak `Nolan remind me to test cancelling`, confirm it, then approve and execute the staged `reminders:create` action so the reminder appears. Speak `Nolan cancel the reminder to test cancelling`. Confirm the read-back says `Cancel reminder “Test cancelling”` and the reminder is still listed. Speak `Nolan confirm`, approve and execute the staged `reminders:cancel` action, and confirm the reminder is gone. Speak `Nolan cancel the reminder to test cancelling` again and confirm nothing is armed (`No reminder matches …`).
12. Speak `Nolan add milk to the errands`, confirm it, then approve and execute it. Speak `Nolan take milk off the errands`. Confirm the read-back says `Remove errand “Milk” from the list` and the errand is still listed. Speak `Nolan confirm`, approve and execute the staged `errands:remove` action, and confirm the errand is gone from the HUD errand list. Execute the same approved action again and confirm nothing else changes.
13. Only after deploying the Convex functions and setting `JARVIS_REMINDER_RESCHEDULE_ENABLED=true`: speak `Nolan remind me to test moving tomorrow`, confirm, approve and execute it. Speak `Nolan move the test moving reminder to tomorrow at 9 am`. Confirm the read-back shows the exact new time and the reminder is unchanged. Speak `Nolan confirm`, approve and execute the staged `reminders:reschedule` action, and confirm the reminder now shows the new time. Execute the same approved action again and confirm the revision does not change a second time. With the flag unset, confirm the same utterance says rescheduling is not enabled yet and stages nothing.
14. Speak `Nolan, give me the rundown`. Confirm the HUD shows and speaks one answer starting `Here's your day.` with today's jobs, due and upcoming reminders, open tasks and open errands that match the HUD panels, and that nothing is staged. Speak `give me the rundown` without the wake word and confirm nothing is answered.

## Latency evidence

The HUD's **Dispatch round-trip** value is measured in the browser from the moment Jarvis begins a final typed/speech dispatch until the voice response JSON is received and parsed. The first dispatch may include voice-session creation. Commands are serialized; time spent waiting behind an earlier command is excluded. It is **not** speech-recognition latency, network-wide tracing, hardware actuation timing, or a claim about recognition accuracy.

Record at least 10 observed dispatch samples with the browser/host and candidate SHA. Report the raw values plus median and worst observed value. There is deliberately no invented pass threshold: establish a baseline on the actual Jarvis host before setting one.

## Pass / stop conditions

Pass only when the maintained CI is green, the OpenAPI contract lints, the voice HUD works through typed fallback, wake-word/final-only behaviour is correct where speech recognition exists, confirmation replay/profile-change cases fail closed, and absent hardware never acknowledges actuation.

Stop commissioning if a partial/ambiguous utterance actuates, spoken confirmation bypasses the governed action boundary, a voice write approves or executes itself, a quote send or other consequential proposal creates an effect, a pending confirmation survives profile/reset/manual override, a remote unauthenticated request reaches a voice route, or unavailable hardware reports success.
