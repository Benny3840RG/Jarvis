Implemented as a queryable, quote-scoped *projection* of delivery state, not a second exactly-once engine: `convex/quoteDeliveryAttempts` (schema + `convex/quoteDeliveries.ts` CAS mutations/queries, indexes exactly as the plan's Step 1 lists) is written to by `quoteSendTool.ts`'s own `execute()` at each lifecycle point (createPending → markExecuting → bindProviderReference → complete/markIndeterminate), while the actual no-blind-retry/exactly-once guarantee remains fully owned by `ToolExecutionService`/`ExternalReconciliationStore` via `context.registerProviderAttempt` — unchanged from #198. A ledger-write failure is logged and swallowed (`project()` helper) rather than thrown, so a projection hiccup can never corrupt the authoritative execution outcome. Added `computeExternalReconciliationId` (exported from `toolExecution.ts`, reusing the existing private hash) so the tool can record the *same* reconciliation ID the engine uses internally, keeping the two stores joinable by `reconciliationId`.

Beyond the plan's listed files, three real gaps were closed along the way:
- **Approval-binding gap** (from Issue #152's own "approval binds to the exact finalized revision fingerprint" requirement, never actually enforced by the original `quoteSendTool.ts`): added a required `expectedRevisionFingerprint` argument, rejected if it no longer matches the current finalized revision.
- **Cross-approval duplicate-send gap**: the generic engine's own replay protection is scoped per idempotency key, so two *different* approved actions targeting the same quote+revision+recipient+channel would both reach `execute()` as legitimately distinct executions. `getBySendScope` is checked before any provider call; any existing attempt for that scope (any status) blocks the send outright with a clear error rather than silently re-sending or faking a replay — retrying after a failure means forking a new revision, not reusing the same finalized one.
- **`GET /api/v1/quotes/:id/deliveries`** now lists real attempts (added `QuoteDeliveryRepository.listForQuote`, wired `ConvexQuoteDeliveryRepository`/`createQuoteDeliveryRepositoryFromEnv` the same way as `createQuoteRepositoryFromEnv`) instead of the permanent 503 from Task 4. The controller strips internal correlation fields (`ownerId`, `sendFingerprint`, `idempotencyKey`, `approvalId`, `actionFingerprint`) before returning attempts — matching the OpenAPI `QuoteDeliveryAttempt` schema, which never listed them.

Not done in this pass, on purpose: no live process ever calls `ExternalReconciliationStore`'s resolution path outside tests/smoke scripts today (`ReconciliationWorker` has no production scheduler wired up anywhere in this repo yet, for any tool), so there's nothing yet to hook a "reconciliation resolved → `deliveries.reconcile()`" callback into. `QuoteDeliveryRepository.reconcile()` is implemented and tested at the repository level, but only reachable by direct calls until a real reconciliation worker exists — tracked as a follow-up, not invented early.
